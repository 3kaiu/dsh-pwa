## CI 仍红：`auto-update-verify.sh` 用例 8 假失败 —— 根因与修复

`e04e88d` 推送后 CI 仍失败，**唯一红点**是「自动更新功能验证套件」用例 8
（dsh 运行中跳过），`✗ dsh 运行中未跳过(rc=0)` + `✗ 运行中仍修改了依赖树`。
`d3748f8`（该用例诞生那次）就已同样失败 → 不是 `e04e88d` 引入的回归，是用例本身在 CI 上从未通过。

### 根因（已在本地实证，非推测）
`tests/auto-update-verify.sh` 的假 /health 服务用 `http.server.HTTPServer`，而
`HTTPServer.server_bind()` 会在 **`bind()` 与 `listen()` 之间**调用 `socket.getfqdn(host)`
做反向解析。解析慢时 socket 停在「已绑定、未监听」状态，**macOS 对此时到达的 SYN 直接丢弃**
（实测：`bind` 后延迟 `listen`，`curl -m 2` 挂满 2.012s 返回 rc=28，而非快速 ECONNREFUSED）。
于是 `update-dsh.sh` 的 `/health`（`-m 2`）与 `/stop`（`--max-time 5`）双双超时 → 读不到
`dsh:true` → 误判「dsh 未运行」→ 照常更新 → 用例假失败。

证据链：
1. CI 用例 8 耗时 **7.9s ≈ 2s + 5s**，正是两个 curl 超时之和（`d3748f8` 那次 8.0s，复现一致）。
2. 同 job 内 `security-verification.sh` 对动态回环端口 curl 全部拿到 200/403 → 网络与 curl 无碍。
3. 同 job 内 `smoke-test.sh` 的占位监听器是**裸 socket**（bind+listen 紧邻）→ 稳定通过。
4. 本机 `getfqdn('127.0.0.1')` 仅 0.007s（mDNSResponder 已缓存）→ 本机永远复现不出来。

### 修复
- `tests/auto-update-verify.sh` 用例 8：假服务改为**裸 socket**（bind+listen 之间不夹任何解析），
  就绪判定由 `sleep 0.3 + kill -0`（只证明进程活着）改为**真连一次 curl 探测**（≤5s，失败打印
  `curl rc=`，区分 7=连不上 / 28=挂到超时）；失败路径补 update.log 尾部诊断。
- `scripts/update-dsh.sh` + `scripts/install.sh`：回环 curl 全部加 `--noproxy '*'`
  （用户环境设了 `http_proxy` 且代理不转发回环时会挂到超时 → 误判 dsh 未运行 → 在用户活跃时
  替换依赖树。本机 `env` 里就真的设了 `http_proxy`）。

### 验证
- 本地全套通过：28 通过 / 9 SKIP（修复前也是 28 通过 —— 说明该用例本机无区分度，是环境依赖型假失败）。
- **负向对照**（skill `ci-gate-hardening` Step 4 要求）：把假服务响应改成 `{"dsh":false}` 跑同一用例，
  如期 `✗ dsh 运行中未跳过` + `✗ 仍修改了依赖树` → 用例仍有区分度，非空转。
- `clang -O2 -Wall -Wextra -Werror` 零告警；`shellcheck -S warning` 零告警；`bash -n` 全通过；
  bats 39/39；`check_run_blocks.mjs` 21 个 run block 零语法错误。

### 教训（可复用）
**假 HTTP 服务一律不要用 `http.server.HTTPServer`**（反向解析夹在 bind/listen 之间，CI 上必踩）。
用裸 socket 或 `TCPServer` 子类覆写 `server_bind` 跳过 `getfqdn`。
**就绪判定不要用 `kill -0`**——它只证明进程活着，不证明端口在 listen；必须真连一次。
**超时时长本身是诊断线索**：实测耗时 ≈ 各 curl `-m` 之和，即可反推是「连接被丢弃」而非「被拒绝」。

## 同一提交暴露出第二个缺陷：更新期被丢弃的唤醒无人重试（CI 冒烟 3b）

修完用例 8 推送后 CI 变红，但换了一个点：**冒烟 3b「并发双 /wake 幂等」卡满 300s**
（`FAIL: 双唤醒后 dsh 未就绪`，20:24:03 → 20:29:05）。同提交 `gh run rerun` 即绿（1m33s vs 7m0s）
→ 时序型，非稳定失败。

### 根因（引导页只发一次 /wake）
- `daemon.c` 守护启动后 10s 触发后台 `update-dsh.sh`；该脚本**在 `npm view` 之前**就持
  `$RT_HOME/.install.lock`（`update-dsh.sh` 第 84 行起）。
- 持锁期间 `spawn_dsh()` 走 `update_locked()` 分支**直接放弃本轮**（设计如此：避免从半更新树拉起 dsh）。
- 但只有 `/wake` 与**页面请求**会 `request_wake()`，`/health` 不会（daemon.c:873 / 904）。
- 引导页 JS 有 `fired` 守卫：**只在首次进入时 POST 一次 `/wake`**，之后仅轮询 `/health`
  （`BOOT_PAGE`，daemon.c:571）。
- 于是那次唯一唤醒被丢弃后**无人重试** → 页面永久停在「正在唤醒…」；冒烟 3b 同样只轮询
  `/health`，遂卡满 300s 超时。命中与否取决于 `npm view` 时长与 `/wake` 时机的竞争
  （该次 CI 整体偏慢：install 23s vs 16s，`npm view` 更慢 → 窗口更宽）。
- daemon.c 原注释写「下次 /wake/页面请求自然重试」——对只轮询 /health 的客户端并不成立。

### 修复
`src/daemon.c`：被锁拒绝时置 `wake_pending`；主循环在 `poll()` **之前**自愈重试（1s 节流，
故完全无连接时也按 poll_ms 推进，不会永久卡住）；`dsh_up()/spawn_pid != 0/runtime 缺失` 时
作废；`/stop` 显式作废 pending。`spawn_dsh()` 在锁仍被持有时只读一次 pid 文件即返回且不计入
崩溃失败计数，故反复调用安全。零常驻语义不变（不 tap_use，空闲仍自退）。

### 回归测试
新增 bats 用例 `wake refused by install lock is retried after lock clears without a new wake`：
持锁 → 唯一一次 /wake → 释放锁 → **只轮询 /health** → 断言 dsh 自愈就绪。
- **fail-before**：`DSH_DAEMON_SRC=/tmp/daemon_prefix.c bats ... -f "retried after lock clears"`
  对修复前源码失败（卡满 12s 无拉起）→ 用例有区分度。
- **pass-after**：对修复后源码通过。

### 验证
clang 零告警（含 universal）；shellcheck -S warning 零告警；`bash -n` 全通过；bats **40/40**
（新增 1 项）；security-verification 33/33；auto-update-verify 28 通过/9 SKIP；
本地冒烟 3b 通过（仅 5/5 `launchctl bootstrap` 因沙箱 I/O error 5 失败，既有环境限制）。

### 教训（可复用）
1. **客户端单次请求 + 服务端「丢弃且不重试」= 永久卡死**。服务端只要可能丢弃请求，
   就必须自己负责重试，不能假设客户端会再来一次。
2. **`gh run rerun` 是区分「稳定失败」与「时序型 flake」的最低成本手段**——先跑它，再动代码。
3. 排查 CI 时**同 job 内其他测试的表现是宝贵对照**：security-verification 对回环 curl 正常、
   smoke-test 裸 socket 占位监听器正常，两条对照直接把「网络问题」排除掉。
4. **测试用的假服务/假监听器一律裸 socket**；`http.server.HTTPServer` 的反向解析坑见上节。

## 收尾:两条 follow-up 落地

### 1. `update-dsh.sh` 的 `npm view` 加网络超时
本脚本在 `npm view` **之前**就持 `.install.lock`，而 npm 无超时参数时 **registry 黑洞（丢包而非拒绝）
会让锁被无限期持有** → PWA 一直停在引导页（守护 `update_locked()` 期间拒绝拉起 dsh）。
- 实测（黑洞 registry `10.255.255.1:81`）：**无参数 >40s 未返回**；加
  `--fetch-timeout=20000 --fetch-retries=1` 后 **3.8s** 按预期中止。
- 取 20s × 2 次 ≈ 40s 上限：检查失败只是「保持当前版本」，下轮再试，代价可接受。
- **只给「检查」加超时，不给 `pnpm update` 加** —— 更新本身耗时长，外部打断会留下半更新树
  （外部 `timeout` 杀 pnpm 会连脚本一起杀掉，备份回滚逻辑根本跑不到）。

### 2. 引导页 `/wake` 由「单次」改为「最多每 2s 重发」
旧实现 `var fired=false` + `if(!fired){fired=true;...fetch('/wake')}` —— 单次 POST 丢包
（`.catch` 缺失，rejection 无人处理）或服务端在更新期丢弃唤醒时，页面永久卡住。
新实现 `var lastWake=0` + `if(nw-lastWake>2000){...fetch('/wake').catch(function(){})}`，
重试按钮改重置 `lastWake=0`。守护侧 `request_wake` 幂等（主进程按 `spawn_pid/dsh_up` 判定，
多个唤醒至多 spawn 一次），故 2s 重发不会产生重复实例。

**为什么服务端重试和客户端重发都要留**：`/health` 不触发 spawn，只轮询 `/health` 的客户端
（冒烟测试即如此）在被拒后永不再发；且**已安装的 PWA 可能仍提供缓存中的旧引导页**，
客户端修复对存量安装不生效。服务端重试是权威兜底。

### 新增回归测试（行为级，非字符串匹配）
`tests/unit/daemon-cases.bats` → `boot page re-fires /wake until dsh becomes ready`：
从 `GET /` 抽出 `<script>`，在 node 里用桩（`fetch`/`document`/`Date.now`/`setTimeout`）驱动
`tick()` 7 轮并统计 `/wake` 次数。
- **fail-before**：修复前源码 → `7 轮 tick 只发出 1 次 /wake`（红）
- **pass-after**：修复后 → 绿
- 附带 `healths >= 3` 断言，防 harness 自身失效导致假绿。
**关键点**：不要用「源码里有没有某个字符串」当门禁——那样抓不住「守卫又被加回来」这类回归；
必须真跑那段 JS。
